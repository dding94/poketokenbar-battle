신뢰 모델: 서버가 전투를 계산하지 않으므로, 앱을 개조한 사람은 숨긴 정보(상대 기술·특성)를 볼 수 있고 거짓 해시로 경기를 VOID로 만들 수 있다. 일치하는 두 보고 없이는 기절·경험치·전적이 바뀌지 않는다. 배틀로 개체가 옮겨지지 않으므로 남의 개체를 빼앗는 위험 자체가 없다(2026-10-30). 반대로 VOID로 기절을 피할 수는 있다. 로컬 육성 수치 위조를 첫 버전 범위 밖으로 둔 것과 같은 급의 위험으로 수용하고, 해시 불일치 횟수를 그룹에 공개해 억제한다.

주의할 기존 특성:

- `activeDexEntry`의 합성 UI ID는 진화 시 바뀔 수 있다. 영속 식별에는 `PokemonProfile.instanceID`를 쓴다(서버는 개체를 등록하지 않는다).

- (폐기, 이전 없음) 타인에게 얻은 개체를 자동 졸업 처리해 `collectedFinals`와 기존 성장 보너스를 올리지 않는다.

### 사전 실측 (2026-10-29)

이 개정을 정하기 위한 조사 증거이며 PR 체크박스를 대신하지 않는다. 재현 가능한 테스트와 CI는 PR 01에서 저장소에 추가한다.

- 엔진: `@pkmn/sim` 0.10.12(Pokémon Showdown 시뮬레이터 추출본, MIT)를 esbuild 0.28.2로 단일 IIFE 번들로 만들었다. macOS 26.5의 Swift `JSContext`에서 보조 코드 없이 실행됐다.
- 결정성: `gen5customgame` 무작위 1:1 2,500판과 200턴 제한을 노린 장기전 200판을 Node 24.14.0과 JavaScriptCore(JIT 켬·끔)에서 실행했다. 정규화 로그(`|t:|` 줄 제외)·승자·inputLog 불일치는 0건이었다.
- 재생: inputLog만으로 다시 실행한 2,700판이 모두 같았다. 3턴 시점 상태 직렬화 왕복도 1,692판 모두 같은 결과였다.
- 성능: JavaScriptCore(JIT) 경기당 평균 1.2ms, 첫 실행은 번들 평가 약 200ms, 장기전 약 17ms였다. JIT가 없으면 경기당 약 7.8ms였다.
- 번들: 최소화 6.6MB(gzip 1.0MB). 미최소화 11.0MB 중 약 8.7MB가 전 세대 학습 기술 데이터로, 전투에는 필요 없을 것으로 보이나 제거는 검증하지 않았다.
- macOS 26.5에서 `JSContext`의 JIT는 `com.apple.security.cs.allow-jit` entitlement로 서명해야 켜졌다.
- 비결정 요소: `Date.now`는 `|t:|` 줄에만, `Math.random`은 seed를 주지 않을 때만 쓰인다.
- 주의: Showdown의 `BattleStream`은 `>eval` 명령을 받는다. 중계받은 텍스트를 스트림에 넣지 않고 검증한 선택 토큰만 `choose()`로 넘긴다. 숨은 정보 때문에 `choose()`가 거절될 수 있으며 거절도 결정적이다.
- 데이터 차이(`@pkmn/dex` 0.10.12, 9세대와 5세대 비교, 1~649번): 일반 특성 24종(그중 13종은 5세대에 없는 특성), 숨겨진 특성 23종, 타입 22종, 종족값 55종이 다르다. 9세대 규칙을 고른 근거다. Showdown 9세대 데이터는 PokéAPI 최신값의 대용이며 직접 대조는 PR 02에서 한다.
- 미검증: 9세대 규칙의 결정성·기술 동작, 다른 macOS 버전의 JavaScriptCore, 실제 두 맥 대전, 학습 기술 데이터 제거.
- 같은 날 저장소의 `engine/probe/`로 옮겨 다시 실행한 결과도 2,500판 불일치 0, 재생·상태 왕복 실패 0이었다. 단, 이름을 바꾸는 최소화 빌드에서는 상태 직렬화 왕복이 100판 중 65판 어긋났고 `--keep-names`로 해결됐다(재현: `engine/README.md`).

### 구성 선택

| 선택지 | 판단 |
|---|---|

## 3. 첫 버전의 사용자 흐름

### 3.1 가입·등록

1. 방장이 회사 그룹을 만들고 만료·회수가 가능한 초대코드를 발급한다.
2. 동료는 코드와 이메일 표시명을 입력한다. 앱은 개인 접속키를 Keychain에 저장하고 복구코드를 보여 준다.
3. 원본 세이브를 보존한다. 개체는 서버에 등록하지 않고, 경기마다 출전 스냅샷을 보낸다.

### 3.2 배틀

2026-10-30 규칙(빼앗기 없음, 정식전만)으로 다시 썼다.

1. 신청자가 그룹 목록에서 상대를 지정하고, 배틀 방식(직접 조작·자동)과 출전 개체를 고른다. 기절한 개체는 고를 수 없다.
2. 상대는 신청자 개체의 공개 정보(종·레벨·타입·능력치·현재 체력 %)를 보고 자기 개체를 골라 수락하거나 거절한다. 신청자는 상대 개체의 공개 정보를 확인하고 확정한다. 레벨 차이는 제한하지 않는다.
3. 시작하려면 양쪽 앱이 같은 엔진 해시로 연결되어 있어야 한다. 직접 조작은 양쪽 사람이, 자동은 양쪽 앱만 있으면 된다. 앱이 꺼져 있으면 도전 만료 안에서 기다린다.
4. 서버가 시작 시점의 전투 스냅샷(현재 체력 포함), seed, 규칙·엔진·정책 버전을 고정한다. 같은 개체는 동시에 한 경기에만 나간다.
5. 직접 조작은 매 턴 양쪽이 30초 안에 기술을 고르고, 서버는 둘 다 받은 뒤 동시에 공개한다. 시간 초과·연결 끊김 턴은 자동 선택 정책이 고른다. 자동 배틀은 모든 턴을 정책이 고른다.
6. 양쪽 앱이 같은 턴을 계산해 같은 화면을 보여 준다. 재접속하면 입력 기록 재생으로 같은 장면을 복원한다.
7. 종료 후 양쪽 앱이 승자와 결과 해시를 보고한다. 일치하면 서버가 결과·전적·연승을 확정하고, 불일치면 VOID로 끝낸다.
8. 확정된 결과를 받은 각 앱이 자기 세이브에 효과를 적용한다.
   - 남은 체력을 저장한다. 진 쪽은 기절이다.
   - 이긴 쪽 현재 포켓몬이 경험치 1천만을 받는다(온라인 하루 10회).
   - 경기마다 한 번만 적용한다.
9. 끝난 뒤 같은 상대에게 재대결을 신청할 수 있고, 상대가 수락해야 성립한다. 그룹 전적판과 챔피언 표시가 갱신된다.

관전은 다음 버전으로 미룬다(2026-10-30).

### 반드시 유지할 조건

- 같은 개체(원본 instanceID)는 동시에 한 경기에만 나갈 수 있다. 서버가 진행 중 경기로 확인한다.
- 다른 그룹의 계정·경기 ID를 알아도 조회·변경 권한이 생기지 않는다.
- 같은 경기의 결과·전적·연승은 한 번만, 양쪽 보고 해시가 일치할 때만 확정한다.
- 확정된 경기의 효과(체력·경험치)는 각 앱이 경기 ID로 한 번만 적용한다. VOID·보류 경기는 효과를 적용하지 않는다.
- 서버는 두 선택을 모두 받기 전에는 어느 쪽 선택도 공개하지 않는다.
- 중계는 선택 토큰(`move 1`~`move 4`, 필요한 경우 `team 1`)만 통과시킨다. 앱은 중계받은 텍스트를 시뮬레이터 스트림에 넣지 않는다.
- 양쪽 엔진 해시가 다르면 경기를 시작하지 않는다.
- 기절한 개체는 신청·수락할 수 없다(로컬 확인 + 서버는 보고된 체력으로 확인).
- 상세 로그 정리와 관계없이 결과 요약과 입력 기록은 유지한다.
- 로컬 육성 수치·체력 위조까지 막는 부정 방지는 첫 버전 범위 밖이다. 동료 간 신뢰를 전제로 한다.

## 6. 세부 정책

### 6.1 초대·개인 접속키·복구

- 그룹은 운영자 비밀값을 아는 사람만 만들고, 만든 사람이 첫 방장이다. 계정 하나는 그룹 하나에만 속한다(2026-10-30).
- 방장만 코드 발급·회수·멤버 제한·재연결 코드 발급을 할 수 있다. 코드에는 만료와 사용 한도를 둔다(초대 기본 7일·30명, 2026-10-30). 방장은 방장을 넘긴 뒤에만 탈퇴한다.
- 접속키는 충분한 엔트로피의 난수로 발급한다. 서버에는 SHA-256/HMAC 해시만 저장한다. 느린 KDF는 무료 CPU 한도를 넘기므로 쓰지 않는다.
- Keychain 항목은 환경(개발·운영)과 상태 폴더별 프로필 ID로 구분해 `PTB_STATE_DIR` fixture끼리 충돌하지 않게 한다. `disableKeychainAccess` 설정을 배틀 키에도 적용할지는 PR 07에서 정한다. 세이브 내보내기에는 키를 넣지 않는다.
- 초대코드 자체를 이후 API의 인증키로 재사용하지 않는다.
- 이메일 중복 입력을 기존 계정 로그인으로 처리하지 않는다. 같은 그룹의 중복 표시명은 안내하고 기존 계정 복구로 연결한다.
- 초기 가입 때 복구코드를 제공한다. 복구 시 기존 접속키를 폐기하고 복구코드도 교체한다. 복구코드는 활동 중인 계정용이다(떠난 계정은 방장 재연결 코드로 돌아온다).
- 방장 보조 재연결: 방장이 특정 계정 전용 일회용 재연결 코드를 발급한다. 사용하면 기존 접속키·복구코드를 폐기하고 그 기록을 그룹에 남긴다.
- 방장이 접속키와 복구코드를 모두 잃으면 운영자가 운영자 비밀값과 그룹 ID로 방장 계정의 재연결 코드를 발급한다. 그 기록도 그룹에 남긴다(2026-10-30).
- 방장이 멤버를 제거하면 열린 초대코드를 함께 회수한다(2026-10-30).
- 초대·복구·재연결 코드 입력은 시도 횟수를 제한한다.
- 접속키·복구코드·초대코드·재연결 코드는 앱 로그, URL, 분석 이벤트에 남기지 않는다.
- 계정 복구와 무관하게 서버의 사용자 ID와 전적은 유지한다.

### 6.2 출전 개체와 결과 효과 (2026-10-30 재작성)

- 서버에 개체를 등록하거나 동기화하지 않는다. 신청·수락 때 그 경기의 전투 스냅샷(종·폼·레벨·IV·성격·특성·기술·성별)과 현재 체력 %만 보낸다.
- 스냅샷의 레벨·IV 범위·종·기술·특성 유효성은 엔진이 검증하고 능력치를 계산한다. 성장 수치와 체력은 동료 간 신뢰한다.
- 출전 대상은 현재 육성 중 개체와 놓아주지 않은 졸업 개체다. 기절한 개체는 고를 수 없다.
- 확정(COMPLETED) 결과를 받으면 각 앱이 자기 세이브에 효과를 적용한다. 효과는 남은 체력 저장(진 쪽은 0, 기절), 그리고 이긴 쪽 현재 포켓몬의 경험치 1천만(온라인 승리 하루 10회, 연습전 한도와 별도)이다. 경기 ID로 한 번만 적용하고, 경로는 PR 03C의 `PracticeBattleEffects`(CompanionStore)를 다시 쓴다.
- 앱이 꺼져 있어 확정을 못 받았으면 다음 접속 때 미적용 확정 결과를 받아 적용한다.
- 체력 회복은 로컬 회복약(PR 03C)으로만 한다. 서버는 체력을 저장하지 않는다.
- 배틀은 도감·보유·원본 세이브를 바꾸지 않는다. AI 사용 로그·프롬프트·회사 코드·원본 토큰 로그는 전송하지 않는다.
- 오프라인에서도 육성은 계속된다. 진행 중 경기의 개체를 회복약으로 고치는 일은 연습전처럼 막는다(PR 03C 판정 재사용).

### 6.3 전투 입력·규칙·정보 공개

- 종·폼, 레벨, IV, 성격, 특성, 성별, 현재 기술을 엔진 입력으로 정규화한다. 이로치 여부는 전투 능력치에 영향을 주지 않는다.
- 9세대 규칙을 쓰고 테라스탈은 금지한다. 지닌 도구는 없음, EV는 0으로 고정한다. PP와 상태이상은 매 경기 정상 상태로 시작한다. 시작 체력은 그 개체의 현재 체력(`config.pN.hp`)이고, 남은 체력은 결과가 확정된 뒤 세이브에 반영한다.
- 종족값·타입·특성은 9세대 데이터를 쓴다. PokéAPI 최신값과 차이가 남으면 출전 화면에 실제 적용 값을 보여 준다.
- 기존에 배운 최대 4개 기술을 유지한다. 기술 편집 UI는 첫 버전에서 추가하지 않는다.
- 지원하지 않는 폼·잘못된 기술·매핑할 수 없는 특성을 조용히 기본값으로 바꾸지 않는다. 등록 자료는 보존하고 출전을 보류하며 이유를 표시한다.
- 출전 전 공개 정보는 종·레벨·타입·능력치·현재 체력 %다. 기술·특성은 배틀 로그에서 처음 쓰이거나 드러날 때 공개한다. 이 숨김은 정상 앱의 표시 규칙이며 보안 경계가 아니다.
- 자동 선택 정책은 양쪽에 같다. 사용 가능 기술·명중·상성·피해 기대값과 정해진 보조기 조건을 평가하고 동률은 전용 seed 난수로 정한다. 별도 LLM 호출이나 유료 AI 서비스는 쓰지 않는다. 정책 버전을 저장한다.
- 상태이상, 우선도, 반동, 회복, 면역, 날씨, PP 소진 등은 엔진 규칙을 따른다.
- 200턴에 도달하면 무승부로 끝낸다(어댑터가 강제). 엔진 자체 1000턴 한도에 의존하지 않는다.

### 6.4 도전·배틀 방·확정

- 상태 흐름: `PENDING → ACCEPTED → READY → RUNNING → REPORTED → COMPLETED`.
- 확정 전 종료: `DECLINED`, `CANCELLED`, `EXPIRED`. 결과를 확정할 수 없는 경기: `VOID`.
- `PENDING`에서 출전 개체가 바뀌면 동의 revision을 올리고 기존 동의를 무효화한다. 성장 진행도 변화는 무효 사유가 아니다.
- 양쪽 앱이 연결되어 `READY`가 되는 순간 엔진 해시와 두 개체의 진행 중 경기 여부를 확인하고, 전투 스냅샷(현재 체력 포함), seed, 규칙·엔진·정책 버전을 한 트랜잭션으로 저장한다.
- 미확정 도전은 24시간 뒤 만료한다(제안 기본값). 수락·취소 경합과 중복 클릭은 DO의 직렬 처리와 멱등 키로 하나의 전이만 성공시킨다.
- 직접 조작 턴 제한시간은 30초다(2026-10-30 확정). 시간 초과·연결 끊김 턴은 자동 정책을 쓰며 양쪽 앱이 같은 선택을 계산한다.
- 재접속한 앱은 저장된 seed·스냅샷·선택 기록을 재생해 같은 장면으로 복원한다.
- 종료 후 양쪽 앱이 승자와 정규화 로그 해시를 보고한다. 일치하면 확정하고, 불일치면 VOID로 끝내며 불일치 기록을 그룹에 공개한다.
- 한쪽 보고가 없으면 그 앱이 다음 접속 때 자동으로 재생·보고한다. 기한(제안 72시간) 안에 보고가 없으면 VOID로 끝낸다.
- 서버 배포로 모든 연결이 끊겨도 방 상태는 DO 저장소에 남아 재접속 후 이어진다. 엔진 해시가 다른 앱 업데이트가 진행 중 경기에 끼어들면 같은 엔진으로 마치거나 VOID로 끝낸다. 다른 엔진 버전으로 조용히 재계산하지 않는다.

### 6.5 결과·기절·경험치·연승·재대결·전적판 (2026-10-30 재작성)

- 확정은 League DO의 `transactionSync()` 하나에서 결과, 전적(승·패·무), 연승, 진행 중 출전 해제를 함께 처리한다. 확정 응답이 유실되면 같은 경기 조회·재시도에서 저장한 결과를 반환한다.
- 기절·체력·경험치는 서버가 아니라 각 앱이 확정 결과를 받아 적용한다(§6.2).
- 무승부는 양쪽의 남은 체력만 반영하고 경험치는 없으며 연승이 끝난다. VOID는 아무것도 바꾸지 않는다.
- 연승은 정식전 승리로 늘고 패배·무승부로 끝난다. 그룹에서 현재 연승이 가장 긴 사람을 챔피언으로 표시한다(동률이면 먼저 도달한 사람, 제안).
- 재대결: 경기가 끝난 뒤 같은 상대에게 같은 배틀 방식으로 바로 신청한다. 상대가 수락해야 성립하고, 기절한 개체로는 신청·수락할 수 없다. 횟수 제한은 없다(제안).
- 그룹 전적판: 그룹 안 트레이너별 승·패·무, 승률, 현재·최고 연승을 보여 준다. 승률은 5경기 이상부터 표시한다(제안).
- 무료 한도나 일시 장애에서는 미확정 결과를 표시하지 않고 보류한다. 복구할 수 없는 경기만 VOID로 처리해 진행 중 출전을 해제한다.

### 6.6 기록·관전·보관

- 경기마다 전투 스냅샷, seed, 선택 기록, 엔진·규칙·정책 버전, 양쪽 결과 해시를 저장한다. 경기당 수 KB다.
- 기록 재생은 저장한 입력을 같은 엔진 버전으로 다시 계산해 보여 준다. 엔진이 바뀐 뒤 과거 경기를 어떻게 재생할지(구버전 엔진 보관 또는 상세 로그 저장)는 PR 11에서 정한다. 과거 경기를 최신 엔진으로 다시 계산해 결과를 바꾸지 않는다.
- 한국어 기술명·상태 메시지를 매핑하고, 미번역 이벤트는 누락하지 말고 읽을 수 있는 대체 표시를 제공한다.
- 관전은 다음 버전으로 미룬다(2026-10-30). 넣을 때는 같은 그룹만, 관전자 앱이 선택 기록을 받아 직접 재생하고 정보 공개 규칙을 똑같이 적용한다.
- 결과를 확인할 수 있는 그룹 범위를 검사한다. 외부 공개 링크는 첫 버전 범위 밖이다.
- 선택적 상세 로그는 90일 후 정리하고 승패·입력 기록 요약은 유지한다.

### 6.7 탈퇴·퇴사

- 본인 탈퇴나 방장 제거 시 접속키를 폐기한다. 서버가 개체를 갖지 않으므로 동결할 개체가 없다(2026-10-30).
- 표시명은 '떠난 트레이너'로 익명화한다. 승패 기록은 서버 ID로 유지한다.
- 방장이 멤버를 제거하면 열린 초대코드를 함께 회수한다. 제거된 사람이 남은 코드로 새 계정을 만들지 못하게 하려는 것이다(2026-10-30). 본인 탈퇴는 초대코드를 건드리지 않는다.
- 다시 합류한 동료는 방장의 재연결 코드로 같은 서버 ID·전적에 돌아온다. 떠난 계정의 복구코드는 쓸 수 없다. 방장이 제거한 사람이 옛 복구코드로 다시 들어오지 못하게 하려는 것이다(2026-10-30).

## 9. 검증 명령과 증거

아래 명령은 **향후 구현 시 실행할 계획**이다. 이번 계획서 작성에서 실행하거나 통과한 명령이 아니다.

### PokeTokenBar 포크

기존 `Package.swift`와 `scripts/test-gate.sh`에서 확인한 명령:

```sh
swift test --filter <변경한 테스트 묶음>
swift build
./scripts/test-gate.sh
```

대상 테스트는 기존 `Tests/PokeTokenBarTests/`의 관례에 맞춘다. 최종 게이트는 전체 Swift 테스트와 기존 코어 커버리지를 확인한다. 커버리지 비율만으로 통과시키지 않고 실제 변경한 실패 분기의 실행을 확인한다. UI 검증은 분리한 저장소로 실행하고 실제 화면 증거를 남긴다.

### 새 `engine/`·`server/`의 제안 스크립트

다음 이름은 현재 존재하는 명령이 아니라 PR 01·04~06에서 정의할 검증 인터페이스다.

```sh
# engine/
npm run build      # 단일 번들 생성과 번들 해시 출력
npm test           # 어댑터·정책 단위 테스트
npm run corpus     # Node와 JavaScriptCore 결정성 코퍼스

# server/
npm run typecheck
npm test           # Workers 런타임 단위·통합 테스트
npm run test:acceptance
```

- 단위: 입력 정규화·기술 선택·상태 전이·결과·효과 적용 정책.
- 결정성: 같은 코퍼스를 Node와 JavaScriptCore에서 실행해 정규화 로그·승자·inputLog를 비교한다. macOS 버전별 결과는 CI 러너로 확인한다.
- 통합: Workers 실행 환경, DO 바인딩·WebSocket·알람·트랜잭션·동시성.
- 인수: 두 사용자 전체 흐름과 장애·복구. 실제 사용자 키나 운영 개체를 테스트 fixture로 사용하지 않는다.
- 성능: 실제 Cloudflare Free 환경의 메시지 CPU·요청·행·연결 수. 테스트 횟수와 환경을 기록한다.
- 증거에는 마지막 관련 변경 이후의 명령·종료 코드·실행 테스트 수·실패/skip·측정값을 포함한다. 테스트 0건, 전부 skipped, 로컬 측정만 있는 상태를 배포 검증 성공으로 보고하지 않는다.

## 부록 A. 전투 엔진 API 계약 (PR 01 초안)

앱은 `JSContext`에 번들 하나를 올리고 전역 `PTBEngine`을 동기적으로 호출한다. 인자와 반환값은 JSON 문자열이며, 경계를 넘어 예외를 던지지 않고 `{"ok":false,"error":"..."}`로 돌려준다. 구현 중 계약을 바꿔야 하면 이 부록을 먼저 고친다.

| 호출 | 내용 |
|---|---|
| `version()` | `{"engine":"@pkmn/sim@x.y.z","adapter":"1","rules":"gen9-notera-noitems-v1"}` |
| `describeSet(set)` | 검증한 SET의 공개 정보 `{speciesNum,species,level,types,stats}`. 9세대 폼/EV 0 능력치를 계산하며 기술·특성은 반환하지 않음(PR 02 추가) |
| `describeMoves(ids)` | 기술 slug/id 1~8개 → `{"moves":[{id,name,type,category,basePower,accuracy(항상 명중이면 null),priority,pp,fixedDamage,variableType}]}`. `fixedDamage`는 레벨·고정량·HP 기반 피해와 일격필살(상성은 면역만 판단, 자속 없음), `variableType`은 전투 중 타입이 바뀌는 기술(잠재파워·웨더볼 등)이다. 9세대 데이터의 순수 조회이며 전투 상태·난수를 쓰지 않는다. 알 수 없는 기술은 `invalid_moves`(PR 03B-3 추가) |
| `typeChart()` | `{"types":[18종],"damage":{공격:{방어:배수}}}`. 타입만으로 계산하고(부유·볼트흡수 같은 특성 면역은 공개 전 정보라 제외) 테라스탈 전용 Stellar는 뺀다(PR 03B-3 추가) |
| `createBattle(config)` | config = `{"seed","policySeed","p1":{"name","set":SET,"policy","hp"},"p2":{...}}` → `{"ok":true,"id"}`. `policy`는 선택 항목으로, 그 진영의 자동 선택 정책 `standard`·`aggressive`·`tactical`·`erratic` 중 하나다(생략 = `standard`, PR 03B-5 추가). 그 밖의 값은 `invalid_policy`. `hp`는 선택 항목으로, 그 진영의 시작 체력이다(PR 03C 추가). 1 이상 그 SET의 최대 체력(`describeSet`의 `stats.hp`) 이하 정수이며 생략하면 가득 찬 채 시작한다. 그 밖의 값과 최대 체력 초과는 맞춰 주지 않고 `invalid_hp`로 거절한다. 시작 체력은 등장(`|switch|`) 전에 넣으므로 등장 줄과 `state`에 다른 체력처럼 보이고(`request`에는 체력이 없다), 상대와 관전자에게는 체력 막대 비율만 보인다. 그 밖의 키는 `invalid_player`. 알 수 없는 종·폼·기술·특성은 오류 코드로 거절 |
| `request(id, side)` | `{"kind":"move"·"wait"·"forced"·"none","moves":[{"slot","id","name","type","pp","maxpp","disabled"}]}` |
| `choose(id, side, choice)` | choice = `{"type":"move","slot":1~4}` 또는 `{"type":"auto"}` → `{"ok":true,"resolved":bool}`. Showdown 거절은 `{"ok":false,"error":"rejected"}`(결정적). 그 밖의 입력은 거절 |
| `autoChoice(id, side)` | `{"slot":n}`, 적용하지 않음 |
| `state(id, viewer)` | viewer = `p1`·`p2`·`spectator`. 양쪽 VIEW: 종·레벨·타입·HP는 항상, 상대 기술은 이미 쓴 것만, 특성은 로그로 드러난 뒤에만 |
| `drainEvents(id, viewer)` | viewer별 최초 기술·특성 공개 이벤트 `{kind,side,id,turn}` 배열(PR 03 추가). 중복 없이 별도 커서로 읽음 |
| `drainLog(id, viewer)` | 그 viewer가 볼 새 프로토콜 줄. 상대의 정확한 HP를 노출하지 않고 `|t:|` 줄을 뺀다 |
| `result(id)` | `{"ended","winner","turns","logHash","inputLog"}`. logHash = `|t:|`를 뺀 전체 로그의 SHA-256 |
| `replay(inputLog)` | 입력 기록으로 다시 실행해 `{"winner","logHash"}`. 검증한 선택 토큰으로 다시 구성하며 `>eval` 같은 스트림 명령을 통과시키지 않는다. 정책 버전이 `auto-v2`가 아니면 `invalid_replay`, 기록 속 config의 정책·시작 체력도 `createBattle`처럼 검증한다 |
| `destroy(id)` | 정리 |

SET = `{"speciesNum","form"(앱 PokemonForm 원시값 또는 null),"level","gender":"male"·"female"·"genderless","nature"(소문자),"ability"(PokéAPI slug),"moves"(PokéAPI slug 1~4개),"ivs":{"hp","attack","defense","special-attack","special-defense","speed"},"shiny"}`. slug에서 Showdown id로의 변환은 영숫자만 남기는 것이 기본이며, 실제 데이터에서 어긋나는 것은 별칭 표로 고정한다.

inputLog v2 = `{version:2,policyVersion:"auto-v2",config,choices:[{side,choice}]}`. config는 받은 그대로(정책·시작 체력 포함, 생략한 항목은 생략한 채) 남으므로 재생도 같은 시작 체력으로 시작한다. 시작 체력을 생략한 전투는 `hp` 추가 전(번들 `ed6bffd4`)과 로그 해시까지 같다. 자동 선택도 실제로 고른 슬롯 토큰으로 기록하므로 재생은 같은 선택을 그대로 다시 넣는다. 이전 버전/정책 기록(`auto-v1` 포함)은 명시적 오류로 거절하며 조용히 새 정책으로 해석하지 않는다.

규칙: 9세대, 테라스탈 금지, 도구 없음, EV 0, 200턴 무승부(어댑터가 강제), 팀 미리보기와 강제 행동(재충전·발버둥)은 어댑터가 처리한다.

폼: 외형만 다른 폼은 기본 폼으로, 배틀 중에만 바뀌는 폼(캐스퐁 날씨 폼, 체리꼬 포지폼, 불비달마 달마모드, 메로엣타 스텝폼)은 기본 폼으로 시작한다. 도구가 필요한 폼(아르세우스 타입, 기라티나 오리진폼, 게노세크트 카세트)은 도구 없는 규칙에서의 동작을 정해 테스트로 고정하고, VIEW에 실제 전투 폼을 보인다.

자동 정책 v1(PR 03에서 확정): 공격기는 위력 × 자속 보정 × 상성(무효면 0) × 명중/100으로 평가한다. 보조기는 효과가 아직 없을 때만 낮은 고정 점수를 주고 능력 상승은 +2까지만 쓴다. 동률은 policySeed·턴·진영으로 만든 전용 난수로 정한다.

자동 정책 v2(`auto-v2`, PR 03B-5): 진영마다 `policy`로 네 성향 중 하나를 쓴다. 모든 무작위는 v1 동률 난수와 같은 policySeed·턴·진영 난수에서 나오며 전투 난수를 쓰지 않는다(Node·JavaScriptCore 동일).

- `standard`: v1과 같은 선택. 무작위 400판(결정 2,500회 이상)에서 고정한 v1 원본 정책과 모든 선택이 같음을 테스트로 고정한다.
- `aggressive`: 위력 × 자속으로 고르고 상성은 무효(0)만 본다(반감·약점 무시). 명중은 4분의 1만 반영한다(명중 70% → 92.5%).
- `tactical`: 체력이 절반 이상이면 아직 효과 있는 상태이상기·자기 능력 상승기를 공격보다 먼저 쓴다(v1 효과 판정, 한 전투 2회까지). 타입 무효는 실제 전투처럼 변화기에 적용하지 않고 무효를 따르는 전기자석파만 막는다(단단해지기는 고스트에게도 쓰고, 전기자석파는 땅 타입에 쓰지 않는다). 절반 미만이면 즉시 회복기(HP 회복 비율 기술·잠자기·달의불빛·아침햇살·광합성)를 먼저 쓴다. 그 밖에는 `standard`.
- `erratic`: 점수가 0보다 큰 기술 중 v1 점수에 비례한 무작위로 고른다(0점은 고르지 않음). 모두 0점이면 `standard`.

- 초대코드 기본값은 7일·30명이다. 방장이 발급할 때 1시간~30일, 1~100명 안에서 바꾼다.
- 방장은 다른 멤버에게 방장을 넘긴 뒤에만 탈퇴한다. 그룹마다 활동 중인 방장은 정확히 한 명이다.
- 계정 하나는 그룹 하나에만 속한다.

구성:

- Worker(`server/src/index.ts`)가 라우팅·입력 검증·비밀값 처리를 맡고 League DO(`League`, SQLite, `idFromName("league")` 하나)를 RPC로 부른다(compatibility_date 2024-04-03 이후). DO 메서드는 동기여도 Worker는 결과를 await한다. API 요청 하나에 DO 호출은 하나다.
- 원문 비밀값(접속키·복구코드·초대코드·재연결 코드·운영자 비밀값)은 Worker에서만 다룬다. Worker가 새 비밀값을 만들고 해시를 계산해 DO에는 해시만 넘긴다. DO는 원문을 받지도 저장하지도 않는다.
- DO의 상태 확인과 변경은 await 없이 동기 SQL로 한다. 여러 문장은 `ctx.storage.transactionSync()` 하나로 묶는다. 그래서 같은 초대코드의 마지막 자리 같은 동시 요청도 하나씩 처리된다.
- 시간은 DO의 시계 하나에서 읽는다. 테스트는 그 시계를 바꿔 만료를 검증한다(실제로 기다리지 않는다).
- 스키마 버전을 저장하고 이후 PR은 테이블을 추가하는 이전 단계로 확장한다.
- 설정은 SQLite DO 이전(`new_sqlite_classes`)과 `workers_dev`다. 비밀값은 `OPERATOR_SECRET`, `CODE_PEPPER` 두 개이며 값은 저장소·문서에 쓰지 않는다. 테스트 값은 낮은 엔트로피의 명백한 가짜 값을 쓴다. Workers Logs(observability)는 PR 05에서 실제로 무엇이 기록되는지 확인할 때까지 끈다. 설정을 생략하면 켜지므로 `observability.enabled = false`를 명시한다.

비밀값 형식과 저장:

| 값 | 형식 | 서버 저장 |
|---|---|---|
| 접속키 | `ptbk_` + 32바이트 난수 base64url | SHA-256 |
| 복구코드 | Crockford base32 16자(80비트), `XXXX-XXXX-XXXX-XXXX` | HMAC-SHA256(`CODE_PEPPER`) |
| 초대코드 | Crockford base32 12자(60비트), `XXXX-XXXX-XXXX` | HMAC-SHA256(`CODE_PEPPER`) |
| 재연결 코드 | Crockford base32 16자, 일회용, 24시간 | HMAC-SHA256(`CODE_PEPPER`) |
| 운영자 비밀값 | 32자 이상. 없거나 짧으면 그룹 생성을 끈다 | 저장하지 않는다(양쪽 SHA-256 다이제스트를 고정 시간 비교. `timingSafeEqual`은 같은 길이만 받는다) |
| 요청 IP | `CF-Connecting-IP` | 시도 제한용 HMAC만, 하루 뒤 삭제 |

코드 입력은 대소문자·하이픈·공백을 무시하고, Crockford 규칙대로 O는 0, I·L은 1로 읽는다. 키·코드는 URL·쿼리·로그·오류 응답에 넣지 않고, 표시 이메일도 로그에 남기지 않는다.

API(`/v1`, JSON 본문, 응답은 `cache-control: no-store`):

| 요청 | 권한 | 내용 |
|---|---|---|
| `GET /v1/health` | 없음 | `{ok:true, api:1}` |
| `POST /v1/groups` | 운영자 비밀값 | `{operatorSecret, groupName, displayEmail}` → 그룹, 방장 계정, `accessKey`, `recoveryCode` |
| `POST /v1/join` | 초대코드 | `{inviteCode, displayEmail}` → 멤버 계정, 그룹, `accessKey`, `recoveryCode` |
| `GET /v1/me` | 접속키 | 내 계정과 그룹 |
| `GET /v1/group` | 접속키 | 그룹 이름, 방장, 멤버 목록. 떠난 멤버는 `status:"left"`, `displayEmail:null`(앱이 '떠난 트레이너'로 표시) |

| `POST /v1/invites/revoke` | 방장 | `{inviteId}` |
| `POST /v1/recover` | 복구코드 | `{recoveryCode}` → 새 `accessKey`·`recoveryCode`. 이전 키·복구코드는 즉시 거절된다 |

| `POST /v1/reconnect` | 재연결 코드 | `{reconnectCode, displayEmail?}` → 새 `accessKey`·`recoveryCode`, 이전 키·복구코드 폐기. 떠난 계정이면 이메일을 다시 받아 같은 서버 ID·전적으로 돌아온다 |
| `POST /v1/leave` | 접속키 | 탈퇴. 방장은 `host_must_transfer` |
| `POST /v1/members/remove` | 방장 | `{trainerId}`. 자기 자신은 안 된다 |
| `POST /v1/host/transfer` | 방장 | `{trainerId}` → 같은 그룹의 활동 중 멤버에게 방장을 넘긴다 |
| `POST /v1/operator/host-reconnect` | 운영자 비밀값 | `{operatorSecret, groupId}` → 그 그룹 현재 방장 계정의 `reconnectCode`(방장이 키와 복구코드를 모두 잃었을 때, 2026-10-30). 그룹 기록 `operator_host_reconnect`를 남긴다 |

- 인증은 `Authorization: Bearer <accessKey>`다. 키가 없거나 틀리거나 폐기됐으면 모두 `unauthorized`다.
- 탈퇴·제거되면 접속키 해시와 이메일을 지우고(익명화) 그 계정의 미사용 재연결 코드를 무효로 한다. 서버 ID와 전적은 남는다.
- 복구코드는 활동 중인 계정의 키 분실용이다. 떠난 계정의 복구코드는 `account_left`로 거절하고, 떠난 동료는 방장의 재연결 코드로만 돌아온다. 방장이 제거한 사람이 옛 복구코드로 다시 들어오지 못하게 하려는 것이다(2026-10-30).
- 같은 그룹에 같은 이메일(대소문자 무시)로 활동 중인 계정이 있으면 가입은 `display_email_taken`으로 끝난다. 기존 계정의 키는 바뀌지도 반환되지도 않는다. 앱은 복구코드 입력으로 안내한다.
- 다른 그룹의 계정·초대·기록은 ID를 알아도 `not_found`로 거절한다.
- 방장이 멤버를 제거하면 같은 트랜잭션에서 열린 초대코드(만료·회수·소진 전)를 모두 회수하고, 초대마다 `invite_revoked` 기록을 남기며, 응답은 `{ok:true, revokedInvites:n}`이다. 제거된 사람이 남은 초대코드로 새 계정을 만들지 못하게 하려는 것이다. 본인 탈퇴는 초대코드를 건드리지 않는다(2026-10-30).
- 운영자 방장 재연결은 그룹 생성과 같은 운영자 비밀값 검사·시도 제한 칸을 쓴다. 순서는 `operator_disabled`(본문을 읽기 전) → 필드 누락 `bad_request` → 시도 제한 → `operator_denied`(셈) → 없는 그룹 `not_found`(세지 않음, 비밀값이 맞을 때만 드러남)다. 틀린 비밀값은 코드를 만들지 않으므로 방장의 기존 코드에 영향이 없다. 발급한 코드는 방장이 발급한 재연결 코드와 같이 동작하고(`created_by`는 `operator`), 기록은 행위자 없이 대상만 방장으로 남는다.

시도 제한: 운영자 비밀값·초대코드·복구코드·재연결 코드의 실패는 IP별·종류별로 15분에 10회까지다. 넘으면 `too_many_attempts`(429, `Retry-After`)다. 형식이 틀리거나 없는 코드, 모든 초대 실패, 떠난 계정의 복구코드(`account_left`), 재연결 실패는 세고, 성공·필드 누락(`bad_request`)·`display_email_taken`·`operator_disabled`는 세지 않는다. 한도에 닿으면 그 IP·종류의 모든 시도가 맞는 코드라도 429다(성공 여부를 흘리지 않으려고). `Retry-After`는 실패 수가 한도 아래로 내려갈 때까지의 초다. 일반 요청 수 제한은 PR 05 실측 뒤 정한다.

입력 검증: 본문은 4KB 이하 JSON이다. 표시 이메일과 그룹 이름은 앞뒤 공백을 빼고 NFKC로 정규화한 뒤 검사하고 그 형태로 저장한다. 표시 이메일은 공백(유니코드 공백 포함)·제어 문자·서식 문자(`\p{Cf}`: 폭 없는 공백, 방향 바꿈, ZWJ, soft hyphen 등)·기본 무시 문자(`\p{Default_Ignorable_Code_Point}`: 한글 채움 문자 U+3164·U+115F, 결합 문자 조이너, 변형 선택자 등)·점자 빈칸(U+2800)을 거절한다. 그룹 이름은 제어·서식 문자만 거절한다(띄어쓰기와 이모지 변형 선택자는 허용, ZWJ 이모지 조합은 불가). 그룹은 운영자만 만들어 이름으로 남을 사칭할 수 없기 때문이다. 같은 사람처럼 보이는 표시명을 막으려는 것이다. 표시 이메일은 3~254자(코드 포인트)이며 `@`가 하나이고 그 양쪽이 비어 있지 않아야 한다. 중복 판정은 정규화한 이메일의 소문자로 한다. 그룹 이름은 1~40자다. 인증 헤더의 `Bearer`는 대소문자를 가리지 않는다.

오류는 `{error:{code}}`와 상태 코드로 돌려준다. 코드는 앱이 번역하는 고정 문자열이다.

| 상태 | 코드 |
|---|---|
| 400 | `bad_request`, `cannot_target_self` |
| 401 | `unauthorized` |
| 403 | `forbidden`, `operator_denied`, `account_left` |
| 404 | `not_found`, `invalid_invite`, `invalid_code` |
| 405 | `method_not_allowed` |
| 409 | `display_email_taken`, `host_must_transfer` |
| 410 | `invite_expired`, `invite_revoked`, `invite_used_up`, `code_expired`, `code_used` |
| 413 | `payload_too_large` |
| 415 | `unsupported_media_type` |
| 429 | `too_many_attempts` |

명령: `npm ci --prefix server`, `npm run typecheck --prefix server`, `npm test --prefix server`. 의존성은 정확한 버전으로 고정하고 잠금 파일을 커밋한다. Node는 CI와 같은 24.14.0이다.

도구(2026-10-30, 공개 14일 이상 지난 판만): `@cloudflare/vitest-plugin` 1.4.4(이전 이름 `vitest-pool-workers`는 지원 종료), wrangler 4.151.1(workerd 1.20261012.1), vitest 4.1.12, TypeScript 7.0.2, `@cloudflare/workers-types` 5.20261012.1, `compatibility_date` 2026-08-01. 테스트는 workerd 안에서 돌고, DO 저장소는 테스트 파일 단위로만 격리되므로 테스트마다 자기 그룹·이메일·IP를 쓴다. `npm audit`의 개발 도구 경고(undici·zod, 배포 코드에는 없음)는 고친 판이 14일을 넘기면 올리고, PR 05에서 `wrangler deploy`를 쓰기 전에는 반드시 올린다.

구현에서 정한 세부 동작(2026-10-30, 리뷰 동의):

- 새 코드에 밀려났거나 계정이 떠나 무효가 된 재연결 코드는 `code_expired`다. 방장이 자기 계정에 재연결 코드를 만들면 `cannot_target_self`다(방장은 복구코드를 쓴다).
- 이미 떠난 멤버를 제거하거나 그에게 방장을 넘기면 `not_found`다. 이미 회수한 초대를 다시 회수하면 200이고 기록은 하나만 남는다.
- 활동 중인 계정의 재연결에서 `displayEmail`은 검증만 하고 쓰지 않는다. 떠난 계정이 이메일 없이 재연결하면 `bad_request`이고 코드는 소모되지 않는다.
- 성공 응답은 모두 200이다. 빈 POST 본문은 `{}`로 읽고(`/v1/leave`), 본문 크기(413)를 형식(415)보다 먼저 본다. 길이 제한 없이 흘러오는 본문도 4KB에서 끊는다.
- 그룹 기록은 최신순으로 최대 200개를 돌려준다. 가입과 복구는 기록하지 않는다.
- 떠난 계정은 `account_left`에 답하려고 복구코드 해시를 남긴다. 접속키 해시와 이메일은 지운다.
- `CODE_PEPPER`가 없거나 비어 있으면 해시가 필요한 요청은 500 `internal`이다(health는 동작). `CF-Connecting-IP`가 없으면 공용 "unknown" 칸으로 센다(Cloudflare는 항상 넣는다).
- HMAC 입력에는 종류 접두사(`invite:`·`recovery:`·`reconnect:`·`ip:`)를 붙인다. 하루 지난 시도 기록은 요청 때와 DO 알람(가장 오래된 기록 + 24시간)으로 지운다.
- 같은 사무실 NAT 뒤의 동료는 시도 제한 칸을 함께 쓴다. IPv6를 /64 단위로 묶는 일은 PR 05에서 일반 요청 제한과 함께 정한다.

## 부록 C. 실시간 연결 계약 (PR 05, 2026-10-30)

구현 중 계약을 바꿔야 하면 이 부록을 먼저 고친다. 부록 B의 비밀값·로그·오류 규칙을 그대로 따른다.

사용자 결정(2026-10-30):

- 접속 상태는 "접속 중"일 때만 보여 준다. 마지막 접속 시각은 저장하지도 보여 주지도 않는다.
- 이번 PR에서 실제 Cloudflare 배포와 무료 실측까지 한다. 그래서 개발 도구를 `npm audit` 경고가 없는 보안 수정판(플러그인 1.4.8 이상, 공개 4일)으로 올린다. 공개 14일 기준의 예외이며 사용자가 승인했다.
- 배포 대상은 측정용 개발 환경(`env.dev`)이다. 운영 환경 배포는 PR 13에서 한다. 계정 로그인(`wrangler login`)과 비밀값 입력은 사용자가 직접 한다.

연결:

- 앱은 `GET /v1/connect`에 WebSocket 업그레이드로 연결한다. 인증은 `Authorization: Bearer <accessKey>` 헤더다(키를 URL에 넣지 않는다). 업그레이드가 아닌 요청은 426 `upgrade_required`다.
- Worker는 키를 SHA-256으로 바꾸고 원문 `Authorization` 헤더를 지운 뒤, 해시만 내부 헤더에 실어 업그레이드 요청을 League DO의 `fetch`로 넘긴다. DO는 활동 중인 계정만 받아들인다. 키가 없거나 틀리거나 폐기됐으면 업그레이드 없이 401 `unauthorized`다.
- DO는 Hibernation API만 쓴다. `ctx.acceptWebSocket(ws, [계정 태그, 그룹 태그])`로 받고, 연결별 정보(계정·그룹·연결 시각)는 `serializeAttachment`에 둔다. DO가 잠들었다 깨도 접속 상태가 남으며, 메모리에만 있는 상태에 기대지 않는다.
- 문자열 `ping`에는 런타임 자동 응답(`setWebSocketAutoResponse`)으로 `pong`을 돌려준다. DO를 깨우지 않으려는 것이다. 자동 응답은 DO를 깨우지 않고 실행 시간도 쓰지 않는다(요청으로 세는지는 문서에 없어 실측한다). 프로토콜 ping도 런타임이 받아 무과금이지만 앱 수준 ping을 기본으로 한다. Cloudflare는 조용한 연결을 끊으므로(문서상 시간 없음, 약 100초로 알려짐) 앱은 30초마다 ping을 보낸다. 마지막 자동 응답 시각은 `getWebSocketAutoResponseTimestamp`로 깨우지 않고 볼 수 있다.
- 같은 계정이 다시 연결하면 나중 연결만 남기고 이전 연결을 4001(`replaced`)로 닫는다. 이때 접속 상태는 바뀌지 않으므로 `presence` 메시지를 보내지 않는다.
- 접속키가 바뀌거나 폐기되면(복구·재연결·탈퇴·제거) 그 계정의 연결을 4003(`revoked`)으로 닫는다. 상태 변경 트랜잭션이 성공한 뒤에 닫는다.
- 앱이 보낼 수 있는 메시지는 PR 05에서 `ping`뿐이다. 그 밖의 메시지가 오면 4400(`unexpected_message`)으로 닫는다. 받는 메시지마다 무료 DO 요청이 쓰이기 때문이다. 배틀 메시지는 PR 06이 추가한다.

서버가 보내는 메시지(JSON 문자열, 모두 `v:1`과 `type`을 가진다):

| type | 언제 | 내용 |
|---|---|---|
| `hello` | 연결 직후 | `{trainerId, groupId, online:[같은 그룹의 접속 중 계정]}` |
| `presence` | 같은 그룹 동료의 연결 수가 0→1 또는 1→0이 됨 | `{trainerId, online}` |
| `group_changed` | 가입·탈퇴·제거·복귀(재연결)·방장 넘기기가 확정됨 | `{kind}`. 앱은 `GET /v1/group`을 다시 읽는다 |

- 접속 상태는 지금 열린 WebSocket(`ctx.getWebSockets(태그)`, 닫히는 중인 연결은 빼고)만으로 정하며 저장하지 않는다(행 쓰기 없음). `GET /v1/group`의 멤버마다 `online`을 더한다. 배포하면 모든 연결이 끊기므로 접속 상태도 비었다가 앱들이 다시 붙으며 채워진다.
- 메시지는 같은 그룹에만 간다. 다른 그룹, 떠난 계정, 닫힌 연결에는 보내지 않는다.
- 메시지와 닫기 사유에는 키·코드·이메일을 넣지 않는다.

구현에서 정한 세부 동작(2026-10-30):

- `/v1/connect` 확인 순서는 405(메서드) → 426(업그레이드 아님, Worker가 인증 전에 확인) → 401이다. Worker는 원래 헤더를 복사해 `Authorization`을 지우고 내부 헤더 `x-ptb-key-hash`를 덮어쓴다(클라이언트가 보낸 값은 무시). DO는 업그레이드와 해시를 다시 확인한다.
- `hello.online`에는 접속한 자신도 들어가며 계정 ID 순이다. 자기 자신의 `presence`는 받지 않는다.
- `group_changed`의 `kind`는 `join`·`leave`·`remove`·`return`(떠난 계정이 돌아옴)·`host_transfer`다. 그룹 생성, 복구, 활동 중 계정의 재연결, 초대 발급·회수, 운영자 방장 재연결은 보내지 않는다. `host_transfer`는 이전 방장을 포함한 모두에게 간다.
- 탈퇴·제거 때는 그 계정의 4003 닫기와 `presence`(오프라인)가 먼저, `group_changed`가 나중이다. 떠난 계정은 그 뒤 아무것도 받지 않는다. 복구와 활동 중 계정의 재연결도 기존 연결을 4003으로 닫는다.
- 닫기 사유는 코드 이름(`replaced`·`revoked`·`unexpected_message`)이다. 클라이언트가 먼저 닫으면 서버가 1000으로 답한다(로컬 workerd에서는 자동 닫기 응답이 보이지 않았다. 실제 동작은 배포 후 확인한다).
- 자동 응답은 정확히 `ping`인 문자열만이다. `PING`, 앞뒤 공백, JSON, 바이너리는 모두 4400이다.
- 시도 제한 칸: IPv6는 `a:b:c:d::/64`(zone id 무시), IPv4는 받은 그대로, IPv4-mapped(점 표기·16진 표기)는 IPv4로, 해석할 수 없는 값은 그 값 자체가 한 칸이다.
- `env.dev`는 `workers_dev`·DO 바인딩·로그 끔(observability)을 다시 적고, 마이그레이션은 상속한다(wrangler 설정 읽기로 경고 없음 확인).
- 테스트는 두 프로젝트다. `api`는 파일 단위 저장소 격리를 그대로 쓰고, `ws`(`test/ws/**`)는 Hibernation WebSocket이 파일 격리에서 동작하지 않아(플러그인 알려진 문제) 격리 없이 한 번에 하나씩 돌며 테스트마다 자기 그룹을 만든다. 테스트 파일 순서는 매 실행 섞는다(Vitest 순서기는 하나라 두 프로젝트 모두). 거절된 연결 응답은 한 도우미로 본문까지 읽고, 끝까지 닫히지 않은 소켓이 있으면 그 파일을 실패시킨다(PR 05 리뷰).
- 측정 스크립트(`server/scripts/measure.mjs`)는 4001·4003·4400이면 다시 붙지 않는다. 세 번 연달아 연결에 실패하면 폴링 대체(10분 뒤 재시도)로 센다. 15초 안에 열리지 않은 연결은 포기하고 다시 시도한다. 멤버는 99명까지, 초대는 1시간·N명으로 만들고 가입이 끝나면 회수한다. 방장은 연결을 열지 않는다. 연결마다 자기 소켓의 이벤트만 처리해 늦게 온 옛 연결의 닫힘이 새 연결을 건드리지 않는다. 첫 Ctrl-C는 설정·연결·대기 어디서든 멈추고 정리한 뒤 요약을 내고(종료 130), 두 번째는 바로 끝낸다. 설정이 중간에 실패하면 초대를 회수하고 가입한 멤버를 탈퇴시킨다. `--cleanup`은 멤버만 탈퇴시키고 방장과 그룹은 남긴다(그룹 삭제 API 없음). 키·코드·비밀값·이메일과 계정 하위 도메인은 출력하지 않는다(요약에는 Worker 이름만). 운영자 비밀값은 `read -rs OPERATOR_SECRET; export OPERATOR_SECRET`로 넣어 셸 기록에 남기지 않는다.

앱의 재접속 규칙(구현은 PR 07. 서버 테스트와 측정 스크립트는 이 규칙을 따르는 클라이언트로 시험한다):

- 끊기면 `min(60초, 1초 × 2^시도 횟수)` 안에서 무작위로 기다린 뒤 다시 붙는다(전체 지터). 60초 이상 연결이 유지되면 시도 횟수를 0으로 되돌린다. 배포로 모든 연결이 한꺼번에 끊겨도 재접속이 몰리지 않는다.
- 4003으로 닫히면 다시 붙지 않고 다시 인증하게 한다. 4001이면 다른 곳에서 접속한 것이므로 자동으로 붙지 않고, 사용자가 팝오버를 열 때 다시 시도한다.
- 연결을 세 번 연달아 열지 못하면 폴링으로 바꾼다. 팝오버가 열려 있을 때만 30초마다 `GET /v1/me`·`GET /v1/group`(이후 PR의 조회 포함)을 읽고, 닫혀 있으면 조회하지 않는다. WebSocket은 10분마다 다시 시도한다. 폴링 중인 사람은 접속 중으로 보이지 않는다.

시도 제한: IPv6 주소는 /64 단위로 묶어 센다(PR 04 리뷰). IPv4는 주소 그대로 센다.

개발 환경 배포·실측:

- `wrangler.jsonc`의 `env.dev`(Worker 이름 `ptb-battle-league-dev`)로 배포한다. `durable_objects` 바인딩은 환경으로 상속되지 않으므로 `env.dev`에 다시 적는다. DO 저장소는 Worker마다 따로라 개발·운영이 섞이지 않는다.
- 순서: 사용자가 실제 Free 플랜(대시보드 Workers & Pages > Plans)을 확인하고 workers.dev 하위 도메인을 등록한다 → 첫 배포 → 비밀값(`wrangler secret put … --env dev`, 값은 사용자가 직접 넣거나 표준 입력으로 만든다) → 측정. 비밀값을 첫 배포보다 먼저 넣으면 DO 없는 Worker가 생길 수 있어 순서를 지킨다.
- 로그인은 최소 권한(`account:read`·`user:read`·`workers:write`·`workers_scripts:write`·`workers_tail:read`)으로 했다(2026-10-30).
- 측정 스크립트(`server/scripts/`)가 측정용 그룹과 가짜 멤버 30명을 만들고 WebSocket 30개를 연다. 유휴·ping·접속 상태 변화·재배포 후 일괄 재접속을 재현한다. 운영자 비밀값은 사용자가 자기 터미널에서 환경 변수로 넘긴다.
- 기록 항목(Worker CPU는 분석의 `workersInvocationsAdaptive` 분위수, DO는 대시보드·`durableObjects*` 데이터셋. Workers 안의 시계는 실행 중에 멈춰 코드 안에서 CPU를 잴 수 없다):
  - Worker·DO 호출별 CPU p50·p99·최대(목표 p99 2ms 이하, 최대 10ms 미만);
  - 연결당·시간당 DO 요청·행 쓰기·GB-s;
  - 자동 응답 ping이 요청으로 세어지는지;
  - 유휴 연결이 끊기는 시간;
  - 재배포 후 재접속 분포.
- 측정할 수 없는 항목은 미검증으로 남긴다.

이 문서는 승인한 설계와 향후 실행할 체크리스트다. 체크박스는 실제 작업과 검증 증거가 생긴 뒤 갱신한다. 구현은 별도의 착수 지시 후 진행한다.
