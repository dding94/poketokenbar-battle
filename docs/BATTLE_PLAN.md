| 전투 기준 | 현재 앱의 기술 습득 기준과 맞춘 5세대 블랙2·화이트2를 출발점으로 사용 |

| 무승부·실패 | 개체 이전 없음 |
| 서버 | Workers(API) + D1(소유권·기록) + SQLite 기반 Durable Objects(배틀 계산) |
| 검증 규모 | 30명, 하루 100경기를 기본 부하 가정으로 검증 |

이메일은 표시값이다. 입력한 이메일을 실제로 소유하는지, 실제 회사 직원인지는 확인하지 않는다. 초대코드가 참여 범위를 정하고 개인 접속키가 소유자를 구분한다. 같은 이메일을 입력했다는 이유로 기존 계정이나 포켓몬에 접근시켜서는 안 된다.

- `activeDexEntry`의 합성 UI ID는 진화 시 바뀔 수 있다. 영속 식별에는 `PokemonProfile.instanceID`와 서버 개체 ID를 쓴다.

- 졸업 개체는 기본적으로 레벨 100이다. 실제 레벨 반영 모드에서 졸업 개체끼리는 기술·타입·성격·IV 등의 차이가 중요하다.
- `DexEntry`만으로는 미성숙 개체의 육성을 완전히 재개할 수 없다. 진화 경로·단계·단계별 사용 성장량 등 `MonState` 정보도 이전 모델에 포함해야 한다.
- 타인에게 얻은 개체를 자동 졸업 처리해 `collectedFinals`와 기존 성장 보너스를 올리지 않는다.

### 비용·호환성 판단

| 선택지 | 판단 |
|---|---|
| **Workers + D1 + 무료 Durable Objects** | 승인한 추천안. 배틀 계산을 분리하고 D1을 소유권의 기준으로 유지 |
| Workers + D1만 사용 | 구성은 단순하지만 일반 Free Worker CPU 10ms 안에 전투 계산까지 완료해야 함 |

공식 문서에서 SQLite 기반 Durable Objects의 무료 제공과 기본 CPU 한도 30초를 확인했다. 이것만으로 Pokémon Showdown이 Cloudflare에서 실행된다고 확정할 수는 없다. 모듈 로딩·파일 접근·동적 의존성·메모리·시작 시간까지 PR 01에서 검증한다.

게임의 전투 처리에는 [Pokémon Showdown 시뮬레이터](https://github.com/smogon/pokemon-showdown)를 우선 검토한다. 공개 Showdown 서버에 경기나 사용자 데이터를 보내지 않고 시뮬레이터 라이브러리만 사용한다. 도입 시 배포된 패키지 버전, upstream commit, 의존성 잠금 파일, 데이터 해시를 고정한다. `master`나 가변 최신 버전에 운영 결과를 의존시키지 않는다.

## 3. 첫 버전의 사용자 흐름

1. 방장이 회사 그룹을 만들고 만료·회수가 가능한 초대코드를 발급한다.
2. 동료는 코드와 이메일 표시명을 입력한다. 앱은 개인 접속키를 Keychain에 저장한다.
3. 원본 세이브를 보존한 뒤 현재 육성 중 개체와 졸업 개체를 서버에 등록한다.
4. 동료를 선택하고 각자 한 마리씩 출전 개체를 정한다.
5. 양쪽 개체·실제 전투 수치·기술·패배 시 이전 조건을 본 뒤 양쪽이 확정한다.
6. 서버가 출전 상태와 규칙·난수 시드를 고정하고 자동 배틀을 수행한다.
7. 결과 저장과 개체 이전을 함께 확정한다. 앱은 같은 결과와 턴별 로그를 표시한다.
8. 승자는 획득 개체를 보유 목록에서 선택해 육성을 이어갈 수 있다.
9. 마지막 개체를 잃은 사용자는 새 스타터 한 마리를 선택한다.

상대 선택 전 미리 한 동의는 최종 출전 조건 동의로 간주하지 않는다. 양쪽의 최종 개체와 전투 스냅샷을 확인하는 절차가 필요하다. 상대가 앱을 꺼도 확정된 경기는 서버에서 완료할 수 있어야 한다.

## 4. 구성 및 책임

| 구성 | 책임 |
|---|---|
| SwiftUI 앱 | 기존 육성, 등록·동기화, 출전 선택·확정, 기록 표시, 받은 개체 육성 재개 |
| Workers API | 개인 접속키 검증, 그룹 권한, 초대·등록·도전·결과 조회, 입력 제한 |
| D1 | 계정·그룹, 개체 소유권, 버전, 도전 상태, 동의, 잠금, 결과, 이전·지급 이력 |
| Battle Durable Object | 고정 입력으로 배틀 계산, 제한된 재시도, 중단 후 재실행. 소유권을 별도로 확정하지 않음 |
| 전투 어댑터 | 앱 데이터와 엔진 모델 매핑, 5세대 검증, 자동 기술 선택, 구조화 이벤트 생성 |

구현 디렉터리 제안:

- 기존 `Sources/PokeTokenBar/Core/`에는 소유권·네트워크·동기화용 작은 구성요소를 추가한다.
- 기존 `Sources/PokeTokenBar/UI/`에는 그룹·출전·확정·기록 화면을 추가한다.
- `server/`에는 TypeScript Workers, D1 마이그레이션, Durable Object, 전투 어댑터와 테스트를 둔다.
- 게임 코드는 이 개인 저장소에만 추가한다. 루트 `AGENTS.md`·`CLAUDE.md`와 기존 Swift 테스트 규칙을 따른다.
- 개발 앱은 별도 번들 ID·앱 이름·저장 경로·실행 잠금 파일을 사용한다. 원본 앱의 자동 업데이트가 개발 앱을 덮어쓰지 않도록 포크 배포 경로를 분리한다.

## 5. 핵심 데이터와 불변 조건

### 데이터 초안

| 모델 | 주요 내용 |
|---|---|
| Trainer / Credential | 서버 ID, 이메일 표시명, 접속키 해시·폐기 상태, 복구 수단 |
| Group / Membership / Invite | 방장·멤버, 코드 해시, 사용 한도·만료·회수 |
| OwnedPokemon | 서버 ID, 원본 instanceID, 현재 owner, ownershipVersion, profileVersion, 상태, 전체 육성 데이터 |
| PokedexHistory | 사용자별 발견·획득·졸업·이전 이력. 현재 출전 가능 여부와 분리 |
| Challenge | 참가자, 선택 개체, 동의 revision, 스냅샷, 만료, 상태, engine/rules/AI 버전, seed |
| BattleResult / Detail | 결과·요약·입력 해시, 턴 이벤트, 적용 데이터 버전, 상세 보관 기한 |
| OwnershipTransfer / StarterGrant | 원인 경기, 이전 전후 소유자, 지급 권리·선택 결과. 중복 방지 키 |
| DispatchJob | D1 경기 접수 후 계산 실행까지의 누락을 복구할 내구성 있는 작업 기록 |

이는 책임을 설명하는 초안이며 물리 테이블 개수를 확정한 것은 아니다. 실제 스키마는 D1 제약과 원자 처리 검증을 거쳐 결정한다.

### 반드시 유지할 조건

- 한 개체에는 현재 소유자가 한 명만 있다.
- 한 개체는 동시에 한 경기에서만 잠길 수 있다.
- 상대 그룹의 계정·포켓몬·경기 ID를 알아도 조회·변경 권한이 생기지 않는다.
- 출전·성장 동기화·이전 판단에는 종 ID나 이메일이 아닌 서버 사용자·개체 ID를 사용한다.
- 같은 경기의 결과와 개체 이전은 각각 한 번만 확정한다.
- 마지막 개체 상실로 발생한 스타터 권리는 같은 원인에 대해 한 번만 생성·사용된다.
- 도감 이력이 남아 있다는 이유로 패배하거나 놓아준 개체를 출전시킬 수 없다.
- 상세 로그 정리와 관계없이 결과 요약, 소유권 이전, 지급 중복 방지 근거는 유지한다.
- 사용자가 수정한 UUID로 복제한 개체와 조작한 로컬 성장 이력까지 증명하는 부정 방지는 첫 버전 범위 밖이다.

## 6. 세부 정책

### 6.1 초대·개인 접속키

- 방장만 코드 발급·회수·멤버 제한을 할 수 있다. 코드에는 만료와 사용 한도를 둔다.
- 접속키는 충분한 엔트로피의 난수로 발급한다. 서버에는 원문을 저장하지 않고 앱에서는 Keychain에 보관한다.
- 초대코드 자체를 이후 API의 인증키로 재사용하지 않는다.
- 이메일 중복 입력을 기존 계정 로그인으로 처리하지 않는다. 같은 그룹에서 중복 표시명 문제는 안내하고 기존 계정 복구로 연결한다.
- 맥 교체·키 유실을 위해 초기 가입 시 복구코드를 제공한다. 복구 시 기존 접속키를 폐기하고 복구코드도 교체한다.
- 접속키·복구코드·초대코드는 앱 로그, URL, 분석 이벤트에 남기지 않는다.
- 계정 복구와 무관하게 서버의 사용자 ID와 개체 소유권은 유지한다.

### 6.2 기존 데이터 등록·로컬 성장

- 원본 세이브의 백업과 schema version을 먼저 확보하고 개발용 복사본에서 검증한다.
- 초기 등록 대상은 현재 육성 중 개체와 놓아주지 않은 졸업 개체다. 도감의 진화 단계 이력을 별개 포켓몬으로 복제하지 않는다.
- 초기 등록은 재시도 가능하게 만들며 원본 instanceID의 중복·이전 소유권을 서버에서 확인한다.
- 새로 부화한 개체와 성장 데이터도 출전 전에 동기화한다. AI 사용 로그·프롬프트·회사 코드·원본 토큰 로그는 전송하지 않는다.
- 성장 수치는 신뢰하되, 레벨·IV 범위·종·기술·특성 유효성은 검증하고 전투 능력치는 서버가 계산한다.
- `ownershipVersion`이 다른 오래된 소유자의 동기화는 거절한다. 낮은 profileVersion의 늦게 도착한 응답이 새 상태를 덮지 못하게 한다.
- 오프라인에서 등록 개체를 키울 수 있지만, 재연결 시 서버 소유권이 먼저다. 다른 사람에게 이전된 개체의 오프라인 성장분을 새 소유자에게 덮어쓰지 않는다.
- 대전 중 개체는 온라인 성장 반영·다른 출전·놓아주기를 잠근다. 소유권이 유지되면 보류한 성장분을 재조정하고, 이전됐다면 이전 버전 쓰기를 차단한다.
- 원본 앱이나 수정한 클라이언트가 로컬에 개체를 표시하는 것까지 막는다는 의미는 아니다. 온라인 소유·출전·이전은 서버 기록을 따른다.

### 6.3 전투 입력·자동 선택

- 종·폼, 레벨, IV, 성격, 특성, 성별, 현재 기술을 엔진 입력으로 정규화한다. 이로치 여부는 전투 능력치에 영향을 주지 않는다.
- 앱에 없는 EV는 0으로 두고 지닌 도구는 없음으로 고정한다. 체력·PP는 매 경기 정상 상태로 시작하고 종료 후 육성 상태에 전투 피해를 남기지 않는다.
- 5세대 기준 타입·종족값·기술·특성을 사용한다. 현재 PokéAPI의 최신 데이터와 차이가 있으면 출전 화면에 실제 적용 수치를 보여준다.
- 지원하지 않는 폼·잘못된 기술·매핑 불가능한 특성을 조용히 기본값으로 바꾸지 않는다. 등록 자료는 보존하고 출전을 보류하며 이유를 표시한다.
- 기존에 배운 최대 4개 기술을 유지한다. 기술을 다시 고르는 편집 UI는 첫 버전에서 추가하지 않는다.
- 양쪽에 같은 자동 선택 정책을 사용한다. 사용 가능 기술·명중·상성·피해 기대값과 정해진 보조기 조건을 평가하며 동률 선택에도 고정 난수를 쓴다.
- 정책은 완벽한 최적 플레이 AI가 아니다. 별도 LLM 호출이나 유료 AI 서비스는 사용하지 않는다.
- 상태이상, 우선도, 반동, 회복, 면역, 날씨, PP 소진 등은 엔진 규칙을 따른다.
- 엔진 버전과 별도로 자동 선택 정책 버전도 저장한다.
- 제안 기술 기본값: 최대 200턴. 엔진의 정상 무승부 또는 턴 제한 도달은 무승부로 끝내고 이전하지 않는다.

### 6.4 도전·확정·실행

- 상태 흐름: `PENDING → ACCEPTED → RUNNING → COMPLETED`.
- 확정 전 종료: `DECLINED`, `CANCELLED`, `EXPIRED`. 복구 불가능한 실행 실패: `VOID`.
- `PENDING`에서 개체·스냅샷이 바뀌면 동의 revision을 올리고 기존 동의를 무효화한다.
- 양쪽 동의 후 접수할 때 소유자·profileVersion·다른 경기 잠금을 다시 확인하고, 실패하면 최신 조건으로 재확인하게 한다.
- 접수 트랜잭션에서 두 개체 잠금, 입력 스냅샷, seed, engine/rules/AI 버전, DispatchJob을 함께 저장한다.
- 제안 기술 기본값: 미확정 도전은 24시간 만료. 확정된 경기에는 이 만료 정책을 적용하지 않는다.
- 수락·취소 경합과 중복 클릭은 상태 조건과 멱등 키로 하나의 전이만 성공하도록 한다.
- D1 접수 후 DO 호출 전에 중단돼도 DispatchJob을 재조회해 실행을 복구한다. 앱 재접속과 제한된 주기 작업으로 누락을 재전달한다.
- 계산은 DB 트랜잭션 밖에서 수행한다. DO가 중단되면 동일 스냅샷·seed·버전으로 처음부터 재실행할 수 있어야 한다.
- DO 메모리나 단 한 번의 호출 성공만을 완료 근거로 삼지 않는다. 재시도는 제한하고, 같은 경기의 중복 실행이 이중 이전으로 이어지지 않게 한다.
- 배포 중 구버전 경기가 남으면 해당 버전 처리 경로를 유지하거나 안전하게 VOID 처리한다. 다른 엔진 버전으로 조용히 재계산하지 않는다.

### 6.5 결과·소유권 이전·스타터

- 완료 처리에서 결과, 이전 원장, 현재 owner 변경, ownershipVersion 증가, 잠금 해제, 승자 도감 획득 이력, 필요 시 스타터 권리를 함께 확정한다.
- D1의 `batch()` 롤백만 믿고 조건부 UPDATE 0행을 성공으로 처리하지 않는다. SQL 제약·검증 가능한 가드로 선행 조건 실패 시 전체 변경을 취소하는 구현을 실측 검증한다.
- 확정 응답이 유실되면 같은 경기 조회·재시도에서 저장한 결과를 반환한다.
- 같은 종이 이미 있어도 승자의 기존 개체를 덮어쓰지 않는다. 획득 개체의 ID·성장 데이터·성격·폼·이로치·진화 상태를 유지한다.
- 이력과 실제 보유를 분리한다. 패자는 과거 도감 기록을 유지하되 출전·육성 대상에서 해당 개체를 제외한다.
- 스타터 권리는 서버 보유 개체가 0이 된 결과 전이에서 생성한다. 첫 가입이나 단순 미등록 상태를 전멸로 처리하지 않는다.
- 스타터를 선택할 때도 보유 상태와 권리 미사용을 다시 확인하고, 중복 요청에는 같은 지급 결과를 반환한다.
- 스타터는 서버에서 새 ID와 유효한 프로필을 생성한다. 기존 알이 있다면 삭제하지 않는다. 활성 개체 변경은 기존 육성 상태를 보존하는 절차로 처리한다.
- 무승부·VOID는 소유권을 바꾸거나 스타터 권리를 생성하지 않는다.
- 무료 한도나 일시 장애에서는 미확정 결과를 표시하지 않고 보류한다. 복구 후 처리하며, 복구 불가능한 경기만 원자적으로 VOID 처리해 잠금을 해제한다.

### 6.6 기록·보관

- 스냅샷·난수 시드·엔진/데이터/정책 버전·입력 해시와 실제 턴 이벤트를 저장한다.
- 기록 재생은 저장한 이벤트를 보여준다. 과거 경기를 최신 엔진으로 다시 계산해 표시하지 않는다.
- 한국어 기술명·상태 메시지를 매핑하고, 미번역 이벤트는 누락하지 말고 읽을 수 있는 대체 표시를 제공한다.
- 결과를 확인할 수 있는 그룹 범위를 검사한다. 외부 공개 링크와 인터넷 전체 공개 기능은 첫 버전 범위 밖이다.
- 상세는 90일 후 정리하고 승패·소유권 요약은 유지한다. 정리된 상세 화면에는 보관 만료를 명시한다.
- 제한을 넘는 로그를 몰래 잘라 확정하지 않는다. 턴·이벤트·응답 크기 상한을 두고 통합 검증한다.

## 7. 무료 운영 검증 기준

아래 수치는 2026-10-28에 확인한 공식 한도다. 구현 착수와 운영 배포 직전에 다시 확인한다.

| 자원 | 무료 한도·조건 | 적용 |
|---|---|---|
| 일반 Workers | 계정 합산 100,000요청/일, CPU 10ms/요청 | 인증·조회·접수 API. 배틀 계산은 DO로 분리 |
| D1 | 5,000,000행 읽기/일, 100,000행 쓰기/일 | 인덱스·페이지 조회·변경분 동기화 |
| D1 공간 | DB당 500MB, 계정 합산 5GB | 첫 버전 단일 DB. 데이터·인덱스·요약 증가까지 산정 |
| SQLite 기반 DO | 100,000요청/일, 13,000 GB-s/일 | 경기 처리만 활성화. 상시 연결·불필요한 타이머를 피함 |
| DO CPU | 기본 30초/호출 | 실제 성능 기준은 이보다 낮게 설정 |
| 주소 | 기본 `workers.dev` | 도메인 구입 없음 |

### PR 01 통과 기준

- [ ] 실제 Free 플랜과 SQLite 기반 DO 사용을 확인한다. 이미 Paid인 계정을 무료라고 간주하지 않는다.
- [ ] 시뮬레이터만 번들링하고, 지원하지 않는 프로세스 생성·네이티브 모듈·동적 파일 로딩 의존성을 해결한다.
- [ ] 기본전·장기전·보조기 반복·특성·날씨·동시 기절·PP 소진을 포함한 고정 테스트 묶음을 만든다.
- [ ] 로컬과 배포 환경에서 동일 입력·동일 버전의 결과·이벤트 해시가 일치한다.
- [ ] 로컬 벽시계 시간과 Cloudflare CPU 시간을 구분해 기록한다. 배포 환경 측정 없이 무료 실행 성공으로 판정하지 않는다.
- [ ] 검증 목표: 일반 API CPU p99 5ms 이하, 검증 최대 10ms 미만. DO CPU p95 1초 이하, 검증 최대 5초 미만.
- [ ] 메모리 목표 96MiB 이하, 플랫폼 시작 시간·번들 크기 제한 준수. 측정할 수 없는 항목은 미검증으로 남기고 통과 처리하지 않는다.
- [ ] 30명·일 100경기·8시간 이용·60초 조회를 기본 부하로 측정한다. 60초 조회만의 예상량은 일 14,400요청이며 실제 작업·재시도·복구 요청은 별도로 더한다.
- [ ] 경기당 실제 저장량과 DB rows_read/rows_written, DO 활성 시간을 측정해 하루·90일·1년 증가량을 계산한다.
- [ ] 동일 계정의 다른 서비스 사용량을 포함해 무료 한도에 충분한 여유가 있음을 확인한다.

### 운영 중 제한 처리

- 상세 10KB × 일 100경기 × 90일은 약 90MB라는 예시일 뿐이다. 실제 스냅샷·이벤트·인덱스·요약을 포함한 측정치로 판정한다.
- 초기 제안값: 상세 보관 공간을 포함해 DB 350MB에서 경고, 400MB부터 신규 경기 접수를 제한하고 기존 처리·복구용 여유를 확보한다. 측정 후 보수적으로 조정한다.
- 앱이 열려 있을 때만 필요한 조회를 하고, 닫히면 빈도를 낮춘다. 상세 로그 전체를 매번 내려받지 않는다.
- API·개인·그룹별 요청 제한과 경기 처리 상한을 설정해 실수로 반복 요청할 때 자원을 고갈시키지 않게 한다.
- 단순 앱 내 사용량 추정은 Cloudflare의 실제 계정 전체 제한을 대신하지 않는다. 대시보드 실제 사용량과 함께 확인한다.
- 무료 한도를 넘으면 오류·보류를 처리한다. 유료 플랜 자동 전환, 유료 외부 API, 새 유료 서비스 추가는 하지 않는다.
- 영구 요약·소유권 이력도 계속 증가하므로 무기한 무제한 무료를 보장하지 않는다. 저장 공간이 부족해지면 신규 접수를 제한하고 보존·이관 방안을 별도로 결정한다.
- 무료 실행 검증에 실패하면 이후 기능 구현을 확대하지 않는다. 원작 재현 범위 축소나 다른 무료 구성을 사용자와 다시 결정한다.

## 8. PR별 작업과 TDD 체크리스트

수작업 변경량은 PR당 대략 200~650 LOC를 목표로 하며 700 LOC를 넘을 것으로 보이면 구현 전에 분할한다. 외부 엔진·잠금 파일을 복사하는 양으로 기능 PR 크기를 판단하지 않는다. 각 PR은 기존 기능을 유지하면서 독립적으로 빌드·관련 테스트를 통과할 수 있어야 한다.

## 9. 검증 명령과 증거

아래 명령은 **향후 구현 시 실행할 계획**이다. 이번 계획서 작성에서 실행하거나 통과한 명령이 아니다.

### PokeTokenBar 포크

기존 `Package.swift`와 `scripts/test-gate.sh`에서 확인한 명령:

```sh
swift test --filter <변경한 테스트 묶음>
swift build
./scripts/test-gate.sh
```

대상 테스트는 기존 `Tests/PokeTokenBarTests/`의 관례에 맞춘다. 최종 게이트는 전체 Swift 테스트와 기존 코어 커버리지를 확인한다. 커버리지 비율만으로 통과시키지 않고 실제 변경한 실패 분기의 실행을 확인한다. UI 검증은 분리한 저장소로 실행하고 실제 화면 증거를 남긴다.

### 새 `server/`의 제안 스크립트

다음 이름은 현재 존재하는 명령이 아니라 PR 01~02에서 정의할 검증 인터페이스다.

```sh
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run test:acceptance
npm run benchmark:cloudflare
```

- 단위: 입력 정규화·기술 선택·상태 전이·결과·지급 정책.
- 통합: Workers 실행 환경, D1·DO 바인딩, 마이그레이션·원자성·동시성.
- 인수: 두 사용자 전체 흐름과 장애·복구. 실제 사용자 키나 운영 개체를 테스트 fixture로 사용하지 않는다.
- 성능: 실제 Cloudflare Free 환경의 CPU·메모리·시작·DB 사용량. 테스트 횟수와 환경을 기록한다.
- 증거에는 마지막 관련 변경 이후의 명령·종료 코드·실행 테스트 수·실패/skip·측정값을 포함한다. 테스트 0건, 전부 skipped, 로컬 측정만 있는 상태를 배포 검증 성공으로 보고하지 않는다.

- [ ] 기존 빌드·배포 환경과 서명·설치 확인 절차.
